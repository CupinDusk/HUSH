# Explicit offline handoff and decision accounting

This is a secondary analysis on the existing 372 admitted source/stub configurations, informed by the R21 PDF reviews. R22_HANDOFF_PROTOCOL.json was fixed before the new script execution. It adds no native experiment, client execution, timing producer or deployment claim.

The producer retains the relation and its reachability/periodicity proof. At a fixed receiver period P, both alternatives use g=gcd(P,d). The mandatory common binding H contains identity, epoch, recurrent-valid-entry horizon, P and d. Changing P requires a new producer query/payload; changing K or phase does not. The completion payload is trusted: equality of supplied witness and represented residue lists does not independently prove that a reachable jointly extremal triple exists.

There are two declared accounting contexts. For a complete new handoff, completion sends Cg,J,A, list lengths, Wg and an exactness status: m+w+5 scalar slots plus H, versus 2t+1 plus H for the profile. For a pre-existing completion interface, Cg,J,A already feed a response-phase consumer (completion-residue envelope and J+A request-to-next-decision bound); the added completion fields are Wg, its length and status, w+2 slots. The exact profile is the default. Completion is selected only when exact and STRICTLY smaller under the chosen context; equal payload selects profile. Query scans m versus t are separately reported, not silently substituted for storage/transport cost. These are declared field counts, not bytes, measured time or production savings.

The separate handoff_consumer.py executable reads only explicitly named context, payload and query JSON. It checks their identity/epoch/horizon/P/d equality, receiver parameters and payload shape. Completion requires trusted exactness status and Wg=Cg. Eight negative controls exercise stale bindings or absent/false status/witness data. This is an implemented offline API prototype, not an OS sandbox, hostile-input security interface or independent reachability checker.

The main p5/ell1/q8/s0=3/P5 cycle selects the five-slot/two-term profile for a full handoff. If its Cg={0},J=9,A=8 already feed the response-phase consumer, it adds Wg={0} and status in three scalar slots and scans one term, obtaining slack 2 at K4/phase0. A complete completion advantage also occurs: the lexicographically first retained case is p9/ell1/s0=0/q16/P9, with recurrent triples (16,27,32),(32,45,48),(48,63,64),(64,81,97), shift81. Its (m,w,t)=(1,1,4), J17/A16 give seven completion versus nine profile slots and one versus four scan terms, slack2 at K4/phase0. The initial s0=0 edge is transient: this example is conditional on valid recurrent entry. The slow-poll P9 example is inexact and correctly selects the three-slot/one-term profile.

All 11,904 raw cycle-period cases are retained, with 35 full/664 incremental completion routes. Deduplicating the EXACT declared key (P,g,J,A,Cg,profile_g) leaves 2,510 interfaces, with 7 full/123 incremental completion routes. All remaining routes select the exact profile. The complete witness/status payload is included, and repeated starting phases are not independent programs. Across ALL physical phases and K1..4 the raw grid has 319952 both-safe / 921 profile-only-safe / 464791 neither-safe queries (785664 total). The deduplicated grid has 72387 / 607 / 94762 (167756 total). Completion-only is impossible by soundness and absent. Thus 569 raw slack-inexact interfaces are not 569 lost safe decisions; the two denominators and observations are distinct.
